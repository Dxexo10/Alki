# Code style preferences

- All colors must come from design tokens / CSS variables defined in the central design system file; no loose hex colors scattered in individual files (only local inline vars like --tabbar-height/--statusbar-height are allowed). Confidence: 0.8
- No emojis and no default/library icons — use custom inline SVG icons that inherit color via currentColor. Confidence: 0.8
- Reuse shared UI components (header, bottom tab bar, phone frame, status bar) identically across all screens rather than redefining them per file. Confidence: 0.75
- Animations/transitions must respect prefers-reduced-motion (e.g. fall back to a short fade instead of a spring/bounce). Confidence: 0.8
- Keep inter-screen links pointing to the correct target file per its name/flow (e.g. a "back" button shouldn't always go home). Confidence: 0.6
- Prefers "liquid glass" / translucent iOS-style surfaces (backdrop blur + subtle top-edge highlight + soft shadow) for persistent bottom bars (tab bar, action bars), applied consistently across every screen that uses them. Confidence: 0.65
- Multi-step forms: the advance/publish button stays visually disabled (dimmed, non-clickable) until all required fields are valid, then enables dynamically without a reload; invalid fields get an inline error state (error-colored border + short helper text below) instead of - Interactive elements' active/selected states must be strongly and clearly differentiated (e.g. active tab/segmented control = solid brand background + on-brand text + shadow, inactive dimmed), and that treatment must be consistent across every screen that has tabs. - Status bar text/icons must use a per-screen color that guarantees contrast against that screen's specific background, rather than a single global theme value. Confidence: 0.6
- Prefers runtime-computed layout values (measure the actual element height with getBoundingClientRect() and expose it via a CSS custom property) over hardcoded magic-number px values guessed per screen; recompute on load/resize so it adapts to content/height changes. Confidence: 0.8
- Shared logic belongs once in a central file (shared.js / design-system.css) and is reused by every screen — not copy-pasted or re-declared per file. Confidence: 0.75
- Tab/state views with genuinely different content must use separate containers toggled independently (display:none/block), not one shared scroll that stacks both views' content. Confidence: 0.85
- Avoid inline style="" attributes (e.g. display:block/flex) that override stylesheet rules — they silently defeat class-based show/hide logic. Confidence: 0.7
- Wants the UI to render correctly on real mobile devices (deployment target), not just inside the desktop preview frame: on narrow viewports the decorative device chrome (black mockup backdrop, rounded frame, fake Dynamic Island / status bar) must be removed so the app fills the viewport, using real safe-area insets (env(safe-area-inset-*)) instead of simulated fixed heights. Confidence: 0.7
- Prefers smooth animated state transitions (e.g. a sliding pill indicator with spring easing plus a short cross-fade) over instant jumps when switching tabs/segmented toggles. Confidence: 0.75
- Inline error/helper text must have comfortable breathing room (extra margin-top + relaxed line-height) so it never looks cramped against the field above it. Confidence: 0.6
- Interactive affordances must be functionally wired (a filter chip must actually filter the list, a toggle must actually toggle, a date field must open a real picker), not merely styled to look interactive. Confidence: 0.75
- When adding a new element/feature, reuse the visual treatment of an existing analogous component (same component family, e.g. matching an existing banner) so it feels part of the design system rather than a new misaligned element. Confidence: 0.7
- New flows should replicate the exact visual AND interaction pattern of an already-working analogous flow (e.g. a new capture step mirrors the working step's camera button, "captured" green-check state, and advance transition) rather than inventing a new one. Confidence: 0.7
- No-data cases must render a designed empty state (icon + short message + suggested action) instead of a blank/broken screen; treat reachable empty states as part of the deliverable. Confidence: 0.7
- Successful actions should show a brief auto-dismissing toast/snackbar confirmation (check icon + short message, ~2-3s) before navigating away, to reinforce the action registered. Confidence: 0.7
- Typography must be consistent across every screen, including newly added ones: display font (e.g. Fraunces) only for large titles, UI font (e.g. Manrope/Work Sans) everywhere else — never fall back to the browser/system default font. Confidence: 0.65
- Local page/component class names must not collide with design-system global class names (e.g. .card, .input-row, .input-label, .chip, .toggle): scope page-specific styles with distinct names and verify no collision exists with the globals before relying on them. Confidence: 0.7
- Form fields must be neutral-bordered by default (untouched state); the error-colored border is reserved strictly for fields that are both "touched" and invalid, never shown on a pristine load, and this rule applies uniformly to every field in the form. Confidence: 0.75
- Use design tokens semantically: a border should reference the border token (e.g. --border-default), not a surface/background token (e.g. --bg-tertiary) even when their color values happen to coincide; pick the token that expresses the element's role. Confidence: 0.6
- Prefers clean, low-noise component styling — avoid stacking redundant decorative layers (an extra ring/border, heavy shadow) on top of a component; when an element looks visually "dirty", simplify it to match the app's standard/sibling components rather than giving it a heavier bespoke treatment. Confidence: 0.65
